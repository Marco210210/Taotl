# Verifica sicurezza Taotl — release 1.0.15

## Ambito e metodo

Analizzati frontend Expo pubblico, frontend amministrativo, API ORDS/PLSQL,
sessioni, sincronizzazione partite, foto e collector degli errori. Test dinamici
con account e dati temporanei propri, richieste HTTP e browser Chromium.
Nessun attacco distruttivo, nessun test di carico sul servizio pubblico.

## Problemi confermati e corretti

| Problema | Evidenza prima della correzione | Correzione e verifica |
| --- | --- | --- |
| Lettura dei log con chiave inclusa nel client | La vecchia chiave pubblica autorizzava la lettura del collector | Chiave privata indipendente e ruotata; vecchia chiave e richieste anonime ricevono 401, chiave privata 200 |
| Partita senza proprietario modificabile da altro account | Il confronto SQL con NULL non negava la scrittura | Controllo esplicito NULL/proprietario e blocco della riga; tentativo rifiutato con 20403 |
| Punteggio arbitrario nella sincronizzazione | Il valore 999999 veniva accettato | Validazione server dei risultati e della formula; tentativo rifiutato con 20400, salvataggio valido e reinvio accettati |
| Profilo privato altrui inseribile in una partita | Era accettato senza classifica associata | Verifica di accesso a ciascun profilo prima della scrittura; tentativo rifiutato con 20403 |
| Stanza propria collegabile a partita altrui | Mancava il controllo del proprietario della partita | Proprietario verificato sul server; tentativo rifiutato con 20404 |
| Upload di HTML come foto | Accettati HTML e MIME arbitrari | Lista formati immagine, firma iniziale e limite 5 MB; HTML e HTML dichiarato PNG rifiutati, PNG valido accettato; nosniff e CSP sulla risposta |
| Blocco del decoder URL | Query con 1500 byte percent-encoded invalidi supera il timeout di 2 secondi in processo isolato | Decoder upstream 0.5.0 adattato a CommonJS; stessa query completata entro il timeout |

La firma iniziale delle immagini non equivale a una decodifica completa del file.
Non è stato dimostrato un XSS end-to-end nel rendering React: il risultato
confermato era l'accettazione di contenuti attivi come foto.
La validazione dei punteggi verifica la coerenza dei dati trasmessi, non può
certificare ciò che è realmente accaduto durante una partita fisica.

## Separazione amministrativa e altre protezioni

- Schermate amministrative e chiamate privilegiate spostate in `admin/`, escluso
  dal resolver Metro pubblico. Servizio web separato solo su loopback e tunnel SSH.
- Il ruolo viene verificato sul server prima di mostrare le schermate protette.
  Un utente normale con cache `isAdmin=true` è stato respinto nel browser.
- Le API amministrative restano sul backend ORDS e richiedono un account admin;
  richieste anonime e token costruiti come payload SQL ricevono 401.
- Gestione degli errori aggiunta agli handler di modifica interessati, con
  risposte JSON e messaggio generico per gli errori interni Oracle.
- Telemetria pubblica marcata non verificata, limiti per IP e globali,
  deduplicazione globale delle notifiche. I controlli SDK restano indipendenti.
- Token di sessione e codici stanza generati con `DBMS_CRYPTO.RANDOMBYTES`.
- `.claude/settings.json`, che conteneva la vecchia chiave pubblica, rimosso
  dall'indice Git e ignorato. Il file locale rimane disponibile; la storia Git
  non è stata riscritta e la chiave storica non autorizza più la lettura dei log.

## Verifiche e limiti

Validazione finale: TypeScript senza errori, 21/21 controlli Expo Doctor,
13 prove Oracle, 19 test del monitor, esportazioni Android/iOS/web e admin web.
Verificate via HTTP le foto valide e gli upload HTML rifiutati. Verificati nel
browser login amministrativo, rifiuto dell'utente normale con cache falsificata,
assenza della pagina admin pubblica e versione 1.0.15 nelle Impostazioni.
I tre pulsanti di avvio partita sono stati azionati ciascuno con un solo clic
fuori dalla freccia su viewport mobile, fino alla schermata delle chiamate.
Questa prova browser non sostituisce un test su un telefono Android fisico.
I tre bundle pubblici esportati non contengono le chiamate amministrative né
le credenziali configurate sul server. Le patch SDK sono allineate a Expo 57.0.24.

La suite Oracle verifica accessi incrociati, upload, SQL injection nel login,
modifiche di partite, punteggi e stanze, includendo casi validi e pulizia dei dati.
I test del collector verificano credenziali, rate limit e notifiche senza invii
Telegram reali. Le query applicative esaminate usano parametri; non è stato
confermato un bypass del login tramite SQL injection nei percorsi testati.

Le patch compatibili di xmldom e brace-expansion sono state installate. Rimangono
avvisi npm moderati transitivi relativi a uuid e agli strumenti che lo includono:
non è stato confermato un percorso sfruttabile dall'utente dell'app. Non sono
stati forzati downgrade di Expo o aggiornamenti incompatibili suggeriti da npm.

Strix 1.6.2 scaricato e CLI verificata; avvio della scansione interrotto dal
requisito Docker, inoltre manca una chiave API LLM dedicata. Nessun risultato
di questo rapporto è attribuito a una scansione Strix completata.
Prerequisiti: https://github.com/usestrix/strix#-quick-start

Questa verifica copre i flussi descritti e non certifica l'assenza di ogni
possibile vulnerabilità o sostituisce un pentest indipendente dell'infrastruttura.
